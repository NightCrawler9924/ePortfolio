01Analog signal path

Amplifier Linearization with Learned Predistortion

UBC undergraduate research · Sept 2026 to present · in progress, no measured results yet

Stage under testLTC6078 op amp, 10 V/V, diode clipped at ±1 V
Dominant distortioncubic (third harmonic)
Correctionpolynomial predistorter, coefficients fit in Python from DC sweeps
AdaptationSDR captures output, re-fits inverse model as temperature and load drift
Design targetthird-harmonic reduction of 10 dB
ToolsLTspice, Python, software-defined radio
  1. Input.The test signal, x(t). The amplifier's curve is measured first from DC sweep data, point by point, which is what the correction is fit against.
  2. Predistorter.A polynomial, a1x + a3x³, chosen to be the inverse of the amplifier's own curve. The coefficients are not derived by hand; they are fit in Python to the sweep data.
  3. Amplifier.An LTC6078 stage at 10 V/V, diode clipped at ±1 V. Past the knee it compresses, and the dominant error is the cubic term. The predistorter has already bent the input the other way.
  4. Output.y(t) should track G·x further into the knee than it would without correction. The design target is 10 dB less third harmonic. No measured number yet.
  5. SDR capture.A software-defined radio samples the real output, not the LTspice model. This is what makes the loop honest about temperature and load drift.
  6. Re-fit.The captured output goes back into the fitter, the coefficients update, and the predistorter tracks the amplifier as it drifts. This is the learned part.
Research log
  1. Sept 2026Project started. Amplifier stage chosen (LTC6078, 10 V/V, clipped at ±1 V). LTspice model built; DC sweep data collected; first polynomial fit in Python.
  2. NextSDR capture of the real output, then the re-fit loop. Third-harmonic measurement before and after correction goes here.

What this is. An amplifier is only linear up to a point. Push the input past that knee and the output no longer follows it, and the error shows up as harmonics, mostly the third. Predistortion means bending the input the opposite way first, so the amplifier's own curve straightens it back out. The interesting part is that the right bend changes as the amplifier warms up, so the correction has to be measured and re-fit rather than set once.

A diode-clipped op amp stage distorts once it passes its compression knee, and the dominant term is cubic. I am designing a polynomial predistortion stage that applies the inverse of that curve ahead of the amplifier so the chain stays linear further into the knee. The model lives in LTspice; the coefficients are fit in Python from DC sweep data rather than derived by hand.

Fixed coefficients drift with temperature and load, so the second half is an SDR feedback loop that captures the amplifier's actual output and re-fits the inverse with a learned predistorter. This entry gets numbers when the loop closes.

02Register transfer level

FaultLatchedPWM

Solo · 2026 · Verilog HDL on Tang Nano 20K FPGA

Functiondeterministic PWM motor controller with latched fault handling
State machineINIT, IDLE, RUN, FAULT, SAFE
Fault responseoutput held low, latched until operator reset
Config guardseparate module rejects out-of-range parameters at load
Flow completedsimulation, synthesis, place-and-route, physical board
  1. INIT.Power-up state. Registers load their defaults and the output is forced low before anything else runs.
  2. IDLE.Waiting for a valid configuration. A separate validation module checks period and duty against their ranges and refuses anything out of bounds, so bad settings never reach the driver.
  3. RUN.PWM is driving the motor. A combinational guard re-checks the parameters every clock cycle; this is the only state where the output can be high.
  4. FAULT.Any violation moves here on the next clock edge, one cycle. The output drops low and the state latches. There is no transition out of FAULT that firmware can trigger, because none was built.
  5. SAFE.Reached only after an external operator reset sequence. Verified in simulation, then in synthesis and place-and-route, then on the Tang Nano 20K board.

What this is. A PWM signal sets how hard a motor is driven. Most controllers check for faults in firmware, which is fine until the firmware itself is the thing that has gone wrong. Here the fault logic is in the FPGA fabric, one clock cycle from the output, and once it latches there is no software path to unlatch it. The point was to build the safety envelope in a place a bug cannot reach.

When a fault asserts, the output drops to a safe state and stays there until an operator resets it, so a transient glitch cannot quietly put the drive back in motion. A separate configuration-validation module rejects out-of-range parameters at load time rather than letting bad settings reach the driver stage. Carried through the complete flow, from simulation to a physical board.

03Architecture & toolchain

RISC-V Toolchain to Hardware Emulation Pipeline

Solo · 2025 · Bare-metal C, RISC-V assembly, gdb

Componentscross-compiler, bare-metal startup, cycle-accurate emulator
Pipeline5 stage, IF/ID/EX/MEM/WB, forwarding and stalling as separate modules
Throughput~1.0 IPC after hazard debugging
Validation25-program regression suite, C and assembly
Built inC

What this is. A processor pipeline works on several instructions at once, one per stage. That breaks when an instruction needs a value the previous one has not finished producing, called a hazard. Forwarding hands the value across early; stalling waits. I wrote the model in C so I could watch every stage every cycle, and wrote the compiler that feeds it so the test programs were real C, not hand-picked assembly.

Most of the work was hazard debugging, tracing execution cycle by cycle in gdb and comparing register state by hand, because a wrong value three instructions later usually originates several cycles earlier.

04Embedded & edge ML

Wildlife-Vehicle Collision Early Warning System

UBC undergraduate research · May 2026 to present · Python, YOLOv8, Raspberry Pi 5, Hailo-8L NPU

ModelYOLOv8n, fine-tuned; mAP50 0.823, mAP50-95 0.638
Dataset7 classes, 3,015 sourced, 2,860 after filtering, fixed-seed split
QuantizationINT8, 2,001-image calibration set, quantization-aware fine-tuning
Camera calibrationOpenCV checkerboard on the mounted unit, 1.34 px reprojection error
Range estimatethin-lens geometry fused with time-to-contact optical expansion
Deploymentsystemd service, self-recovering; cold boot to first detection ~45 s
Tests47 unit tests, run without hardware via simulation backend
  1. Camera.Mounted on the unit and calibrated in place with an OpenCV checkerboard: 1.34 px reprojection error. This replaced a placeholder focal length that every earlier distance number had silently depended on.
  2. Detector.YOLOv8n fine-tuned on a 7-class dataset I built (2,860 images after filtering), then quantized to INT8 with a 2,001-image calibration set and quantization-aware fine-tuning. The Hailo compiler refused the first export; the fix was explicit end-node parsing and a custom NMS config.
  3. Range.Two estimates fused conservatively: thin-lens geometry from the calibrated focal length, and time-to-contact from how fast the box grows frame to frame.
  4. Alert.Drives the warning output over GPIO and the I2C display. The display driver got retry and graceful degradation after the connector proved flaky.
  5. Service.The whole pipeline runs as a systemd unit that restarts itself. Verified by cold boot, detecting about 45 s after power-on with no manual steps. 47 unit tests run without the hardware through a simulation backend.

What this is. A camera on a roadside unit watches for animals and warns drivers. It has to run on a small board with no network, so the detection model is shrunk from floating point to 8-bit integers and moved onto a dedicated accelerator. Shrinking a model loses accuracy unless it is done carefully, which is what the calibration set and the quantization-aware fine-tuning are for. The rest of the work was making it survive real hardware: a service that comes back on its own after a power cut, and tests that run without the board attached.

The Hailo compiler refused the model. I traced it to an incompatible automatic postprocess-extraction step and rebuilt the export path with explicit end-node parsing and a custom NMS configuration rather than working around it. The camera calibration replaced a placeholder focal length that every prior distance measurement had silently depended on.

Bugs fixed on the real unit: a SIGTERM handler bypassed by a vendored library, a non-daemon thread that hung shutdown, a race between the alert thread and hardware cleanup (confirmed with a 20-trial stress test, fixed with a lock and idempotent teardown), a flaky I2C connector, and an apparent startup hang that was stdout block-buffering.
